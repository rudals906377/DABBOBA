# DABBOBA 내부 테스트 결제

## 승인 범위

2026-09-12: 실제 돈이 나가지 않는 앱 내부 테스트 결제와 예시 상품을 사용한다. 기존 상품 원본을 보존할 필요는 없다는 사용자 결정을 반영하되, 과거 주문·추첨·사용자 기록은 삭제 대상이 아니다. 기존 DABBOBA Supabase 프로젝트를 사용하고 고정 실행 파일은 유지한다.

## 구현 경계

- 명시적으로 선택한 `supabase-demo` 프로필에서만 테스트 기능을 연다. 일반 통합·운영 프로필에는 테스트 결제나 임의 로그인 우회가 없어야 한다.
- `supabase-demo` 프로필은 저장소 루트의 `.env` 대신 git에 올라가지 않는 `.env.supabase-demo.local`에서 데모 프로젝트 접속 값을 읽는다. 두 프로필의 대상 프로젝트가 다르므로 `.env`는 통합 프로필 전용으로 두고, 두 파일을 동시에 준비해 둘 수 있다.
- 내부 고객 계정은 `da000000-0000-4000-8000-00000000000a` / `member01@dabboba.local` 하나만 `ACTIVE`로 유지한다. 이 계정의 가격·재고·추첨 결과·보관함·포인트는 서버 트랜잭션으로 저장한다.
- UUID와 이메일은 고정된 내부 테스트 식별자지만 닉네임 등 프로필 정보는 일반 고객과 동일한 수정 가능 데이터다. 프로필 변경을 계정 불일치나 초기화 사유로 삼지 않는다.
- 고객 화면에는 `DEMO`, 테스트 계정 문구, A/B 계정 선택기를 노출하지 않는다. `TEST_PG`와 실제 청구가 없다는 안내는 사실성을 위해 개발 전용 결제 컨트롤 안에서만 표시한다.
- 중복 내부 계정은 로그인을 차단하고 기존 세션을 폐기해 퇴역시킨다. 주문·결제·추첨·보관함·포인트 원장·감사 이력은 원래 사용자 ID에 그대로 보존하며 계정을 병합하거나 하드 삭제하지 않는다.
- 모바일 고객 경로는 퇴역한 `mobile-test@dabboba.local` 계정을 자동 생성·복구하거나 연결 실패 시 대체 계정으로 사용하지 않는다. 유효한 단일 계정 세션이 없으면 게스트 상태를 유지한다.
- 실제 카드정보 입력, PG 결제/환불 호출, 배송장 구매, SMS·메일·푸시 발송, Worker/Cron 활성화는 하지 않는다.
- 단위·동시성·초기화 테스트는 폐기 가능한 로컬 TEST DB에서 한다. Supabase에서는 사용자가 승인한 예시 레코드만 대상으로 횟수가 제한된 기능 검증을 한다.

| 동작 | 완료를 판단하는 증거 |

| 프로필 | 닉네임 변경 뒤에도 같은 UUID·이메일의 고객으로 유지되며 결제·보관함 이력 보존 |

| 포인트 환급 | 직접 뽑은 보관 중 가챠만 처리, 불변 원장과 잔액 일치 |
| 배송 신청 | 고객이 직접 저장한 배송지와 선택 상품만 신청 기록에 저장; 외부 발송 없음 |

| 화면 | 네이티브 앱의 일반 고객 동선에 `DEMO`·테스트 계정·A/B 선택기가 없고, 개발 전용 결제 컨트롤에만 `TEST_PG`·실제 청구 없음 표시 |

위 표는 검증 기준이며 완료 보고가 아니다. 실제 실행 결과는 아래에 별도로 기록한다.

## 검증 기록

- 구현 전 원격 읽기 확인: 상품 25개, 사용자 1명, 주문 1개, 추첨 결과 4개. 기존 거래 기록은 그대로 둔다.
- 연결 변경 전 기준 검사: 격리된 `127.0.0.1:55441/dabboba_edge_test`에서 commerce, kuji-rooms, kuji-slots, exchange, account-shipping 통합 검사 5/5 통과(건너뜀 0). 기존 모바일 주문 복구·쿠지 주문·교환 검사 24/24 통과. 이는 새 데모 기능의 완료 증거와 구분한다.
- 보호된 런타임 28개 파일 무결성 검사, 기존 프로필/테스트 환경 안전 검사 9/9, 공용 패키지/API 빌드와 웹 빌드 통과. 웹 빌드에는 기존 대형 번들 경고가 남아 있다.
- 구현·실행 검증 진행 중. 실제 PG 결제, 실물 배송, 외부 인증·알림, 스토어 출시 완료를 의미하지 않는다.
- 2026-09-12 Supabase staging 확인: canonical 고객 1명만 `ACTIVE`, 중복 내부 계정 2명은 `BANNED`, 기존 활성 세션 13개는 폐기했다. 중복 계정의 기존 주문 3건과 보관 상품 5개는 원래 사용자 ID에 보존했고, 자동 생성 배송지 2개만 제거했다.
- 2026-09-24 분리된 로컬 TEST DB `dabboba_flow_test_20260924`에서 현재 내부 카탈로그 허용 ID에 맞춘 예시상품 A(가챠)·B(쿠지)를 사용해 `node scripts/verify-demo-commerce.mjs --run`을 실행했다. 57개 API 요청에서 TEST_PG 승인·실패·취소·환불, 가챠 결과/보관함/포인트, 쿠지 방 입장·번호 예약·결과 저장을 검증했다. 이 결과는 원격 Supabase나 실결제 증거가 아니다.
- 재현 가능한 로컬 시드 `scripts/seed-local-demo-commerce.mjs`는 `DABBOBA_LOCAL_DEMO_DATABASE_URL`로 지정한 `127.0.0.1:55433` 또는 `:55441`의 `dabboba_flow_test_*` DB와 명시적 `--run`에서만 동작한다. `예시상품 A (가챠)`·`예시상품 B (쿠지)`, 홈의 가챠·쿠지 예시 섹션, 봉인된 쿠지 덱을 만들고, 추첨 구성이 게시된 뒤에만 두 상품을 `ON_SALE`로 전환한다. 기존 상품과 ID가 충돌하면 거래 데이터를 덮어쓰지 않고 실패한다. 시드 명령 자체의 새 DB 재실행은 아직 별도로 확인해야 한다.
- `scripts/supabase-demo-seed.sql`의 과거 `demo-test-gacha`·`demo-test-kuji` 판매 상품은 현재 API의 내부 판매 허용 목록과 일치하지 않는다. 해당 원격 시드의 `--apply`를 재실행해 이 검증 결과를 재현하려 하지 말 것. 원격 예시상품 적용은 기존 상품·주문·계정·확률표를 먼저 읽기 전용으로 대조하고, 공개 카탈로그 노출 경계를 별도로 검증한 뒤 승인된 마이그레이션으로만 한다.
- 사전오픈 시뮬레이터의 결제·뽑기 진입 차단은 의도된 동작이다. 이 화면의 구동이나 코드/상태 테스트만으로 개발용 TEST_PG 네이티브 결제 버튼, 가챠 레버, 쿠지 종이 모션의 실기기 동작을 검증했다고 주장하지 않는다.
- 2026-09-24 재검사: 결제·가챠·쿠지 관련 로컬 상태/계약 검사 199개와 전체 단위 검사 825개가 통과했다. TEST_PG 승인 응답이 멈추는 경우를 새로 재현해 8초 후 중복 결제 주의·주문 상태 확인 안내로 복구하도록 고쳤다. 현재 격리 DB 역할 URL과 `127.0.0.1:8788` API가 없어서 57요청 서버 흐름은 이 회차에 재실행하지 못했다. DABBOBA SDK57 시뮬레이터는 홈 상품 API 오류를 표시하므로 예시상품 선택부터 네이티브 결제·가챠·쿠지 결과까지의 화면 검증도 아직 미완료다.
- 2026-09-24 추가 검수: `supabase-demo`가 선택된 전용 개발 실행에서만 앱의 `EXPO_PUBLIC_COMMERCE_CAPABILITY=LIVE`가 설정되도록 연결했다. 일반 로컬·Supabase 통합 실행은 `PRELAUNCH`이며, 서버의 `LIVE` 공개 설정과 정확한 `TEST_PG` capability가 없으면 앱은 여전히 차단한다. 실행 설정 검사 34개와 전체 단위 검사 835개, 모바일 타입 검사, 런타임 무결성 검사가 통과했다. 원격 DB의 migration ledger는 `0051_home_catalog_section_layout.sql`에서 멈춰 있어 `0054`의 `sale_status` 컬럼이 없었다. 원격 상품 ID 두 개는 이미 실제 상품(귀멸의 칼날 오네무탄 13형, 실바니안 어드벤쳐 쿠지)으로 사용 중이라 예시상품 A·B로 덮어쓸 수 없다. Docker Desktop의 로컬 소켓도 응답하지 않아 격리 DB 시드와 57요청 서버 검사를 이번 실행에서 재현하지 못했다. 시뮬레이터 홈은 실제로 상품 API 오류를 표시했다. 원격 migration 적용이나 예시상품 쓰기는 수행하지 않았으며, 앱에서 상품 선택→테스트 결제→가챠·쿠지 뽑기 모션→결과 표시의 전체 화면 검증은 미완료다.
- 2026-09-24 후속 재검증: Docker 관리 소켓은 계속 타임아웃이지만 로컬 PostgreSQL `127.0.0.1:55433`은 접속 가능했다. 기존 격리 DB `dabboba_flow_test_20260924`에 현재 migration 0065, 내부 계정 1개, 판매 가능한 예시상품 2개, ACTIVE 가챠·쿠지 추첨 설정, 봉인 쿠지 슬롯 10개가 있음을 확인했다. 격리 DB 안에서만 두 상품명을 검증기의 표준 `예시상품 A (가챠)`·`B (쿠지)`로 맞추고 예시 홈 섹션 2개를 추가했다. 원격 Supabase에는 쓰지 않았다. 로컬 owner 연결을 사용하는 `node scripts/run-isolated-demo-api.mjs --run`으로 TEST_PG API를 기동했고, `node scripts/verify-demo-commerce.mjs --run`이 59개 요청의 6개 시나리오(가챠 승인·결과·중복 방지, 실패/취소 재고 복구, 미사용 권리 환불, 포인트 환급, 쿠지 방·주문·번호 선택·결과)를 통과했다. 이 결과는 격리 DB의 서버 흐름 증거이며 runtime/worker 최소권한, 실결제, 네이티브 애니메이션 터치·시각 검증 증거는 아니다. 네이티브 직접 조작은 Mac 잠금 해제로 아직 수행하지 못했다.
- 같은 격리 API가 실행 중일 때만 `node scripts/dabboba-mobile-launch.mjs --ios --demo-commerce`를 사용한다. 이 옵션은 iOS/Android 로컬 개발 실행에서만 앱의 LIVE 화면을 열며, 일반 사전오픈 앱·원격 인증 실행과 함께 사용할 수 없다. Xcode 설치에 Simulator.app 창이 없어도 부팅된 전용 Simulator에는 앱 URL을 전달한다.
- 2026-09-24 네이티브 화면 관찰: SDK57 iPhone 17 Pro Simulator에서 홈의 예시상품 A, 가챠샵과 쿠지샵, 두 상품 상세, 가챠 결제 화면의 이미지·가격·재고·TEST_PG 문구를 확인했다. 기존 소비 완료 권리의 딥링크로 가챠 상품 오픈 대기 화면과 쿠지 봉인 티켓 대기 화면도 표시됐다. 쿠지 결제 URL을 대기실 없이 직접 열면 안내와 재시도가 표시됐다. 상세의 내부 `DEMO-TEST-*` SKU 배지를 제거한 뒤 두 상품 화면에서 사라진 것을 확인했다. 자동 테스트는 단위 836개와 API TypeScript 6개, 모바일·API 타입 검사, 실행 옵션 검사 23개가 통과했다. 다만 Mac이 잠겨 Simulator 터치 조작이 불가능했으므로 실제 상품 탭→동의→TEST_PG 버튼→가챠 레버/쿠지 종이 모션→결과 화면의 네이티브 연속 동선은 통과로 표시하지 않는다.
