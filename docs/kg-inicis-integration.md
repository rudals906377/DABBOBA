# KG이니시스 결제 연동

## 선택과 이번 범위

2026-09-09 사용자가 PG로 **KG이니시스**를 선택했다. 최초에는 KG 공식 API 직접 연동을 준비했으나, 이후 사용자가 포트원 계정을 제공하며 이를 참고해 진행하도록 요청했다. 포트원에서 이미 KG 신청이 진행 중임을 확인했으므로 **후속 결제 연동 계획은 PortOne V2 → KG이니시스**를 우선한다. 아래 DBB017 직접 조회 구현과 INIpay PRO 자료는 이전 구현·참고 기록으로 보존한다. Google Cloud 작업은 하지 않으며, 계약·비용·실거래·배포 승인을 의미하지 않는다.

DBB017의 범위는 **거래 상태 조회를 기존 worker에 연결**하는 것이다. 인증 결과 수신, 최초 승인 요청, 고객 결제창, 취소·환불 요청은 별도 후속 단계다. 기존 API의 `PAYMENT_PROVIDER=UNCONFIGURED`를 유지한다. 조회 기능이 생겼다고 주문 생성이나 결제 기능을 켜지 않는다.

## 최신 준비 상태 · PortOne 경유 · 2026-09-09

사용자가 지정한 공식 포트원 계정의 관리자 화면을 직접 확인했다. 아래는 해당 시점의 화면 상태이며 계약 완료나 결제 테스트 증거가 아니다.

- 사업자 정보 등록과 결제대행사 신청은 완료 표시다.
- KG이니시스 **신용카드 일반결제는 입점 심사중**이다.
- 대표상점의 실연동 채널과 테스트 채널 모두 `등록된 채널이 없습니다`로 표시됐다. 아직 앱이 사용할 KG 채널을 확인하지 못했다.
- 실연동 설정 화면은 포트원 이용료 결제 카드 등록이 필요하다고 안내했다. 비용 조건과 카드 등록은 사업 운영자가 실제 적용 시점에 확인한다. 카드를 등록하거나 요금제에 동의하지 않았다.
- API 비밀키와 webhook 비밀키는 열람·발급·저장하지 않았다. 채널 생성, 설정 저장, 실제 결제, 운영 DB 변경도 하지 않았다. 로그인 정보는 이 문서와 환경 파일에 저장하지 않는다.

### 적용 구조와 직접 연동 자료의 구분

앱은 포트원 SDK로 KG 결제창을 열고, 서버는 포트원 API로 실제 결제 상태를 조회·검증한 뒤 DABBOBA 원장을 확정하는 방향이다. DB·인증·파일·API·자동 작업의 Supabase 중심 전환은 그대로 유지한다. 포트원은 Supabase를 대체하는 DB/서버 서비스가 아니다.

[포트원 KG이니시스 V2 가이드](https://developers.portone.io/opi/ko/integration/pg/v2/inicis-v2)의 `inicis_v2`와 아래 INIpay PRO 직접 호출 규격을 같은 인터페이스로 취급하지 않는다. 승인된 MID가 포트원의 어떤 채널·모듈에 연결되는지 확인하고, 포트원 거래에 직접 PRO 승인/망취소 요청을 중복 실행하지 않는다. 기존 `KG_INICIS` 거래를 포트원 거래로 재해석하거나 직접 조회 adapter를 일괄 교체하지 않는다. 신규 연결 시 제공자·채널·환경·거래 식별자 구분을 명시적으로 설계한다.

### 다음 구현 순서와 준비 항목

1. **채널 준비:** 포트원 V2에서 지원하는 KG 테스트 채널과 계약 모듈을 확인한다. 테스트/실연동을 분리하고 사용 가능한 Store ID·Channel Key를 연결한다. 계정 비밀번호는 앱 연동 수단이 아니며, 서버용 V2 API Secret과 webhook 서명 비밀은 별도 보안 설정으로 관리한다. INIAPI Key·PRO Hash Key와 혼용하지 않는다.
2. **서버 결제 계약:** 인증된 사용자의 서버 주문에서 금액·통화·고유 결제 ID를 결정한다. 앱의 성공 화면만 믿지 않고 [공식 서버 완료 처리](https://developers.portone.io/opi/ko/integration/start/v2/checkout?v=v2)에 따라 포트원 결제를 조회한다. 주문 소유권·연결된 결제 ID·상점/환경·금액·통화·최종 상태를 대조한 뒤 같은 트랜잭션에서 결제/주문/재고/포인트/추첨권을 한 번만 반영한다.
3. **결제 통보와 복구:** [V2 webhook 가이드](https://developers.portone.io/opi/ko/integration/webhook/readme-v2?v=v2)에 맞는 서명 검증과 중복 방지 경계를 추가한다. 현재 generic `x-dabboba-signature` 검증을 포트원 서명 검증으로 간주하지 않는다. 앱 복귀 누락·통보 중복/순서 역전·조회 실패·예약 만료 후 결제 성공도 다룬다. 서명 검증용 원문과 비밀을 로그에 남기지 않는다.
4. **앱 결제창:** [공식 모바일 V2 가이드](https://developers.portone.io/opi/ko/extra/mobile-payment/readme-v2?v=v2)의 `@portone/react-native-sdk`를 우선 검토한다. 현재 Expo 버전·네이티브 빌드와의 호환성, iOS/Android 결제앱 호출 및 복귀는 별도 검증한다. SDK 존재만으로 Expo Go나 실기기 동작을 보장하지 않는다.
5. **취소·환불·대사:** 포트원 거래에 맞는 조회/취소 adapter와 기존 보상 원장을 연결한다. 전액/부분취소, 이미 사용한 포인트·추첨권·배송 상태, 불확실한 응답과 재시도 시 중복 환불 방지를 확인한다. 직접 KG 조회 구현의 로컬 통과 기록으로 이를 대체하지 않는다.
6. **마지막 검증과 운영 전환:** 합성 응답/로컬 DB 회귀 후 격리된 테스트 채널에서 결제→서버 확인→추첨권→취소와 실기기 왕복을 확인한다. 심사 승인, 비용 확인, 실연동 채널/비밀 준비 및 운영 적용 승인까지 갖춘 뒤에만 결제를 활성화한다. 그전에는 `PAYMENT_PROVIDER=UNCONFIGURED`를 유지한다.

앞선 계정 확인 단계에서는 문서만 갱신했다. 아래 DBB020은 그 뒤 시작한 로컬 서버 코드 단계이며 실제 계정 연결·거래와 구분한다.

### DBB020 · 독립 서버 adapter · 로컬 검증

`apps/api/src/lib/portone-v2.ts`와 `portone-webhook.ts`를 추가하고 공식 서버 SDK를 `0.19.0`으로 고정했다. SDK의 서명 검증을 사용하며, 조회·취소는 공식 REST 주소에 시간/응답 크기 제한을 적용한 `fetch`로 호출한다. 해당 SDK 버전의 조회 client가 호출별 AbortSignal/전송 함수를 받지 않기 때문에 전역 `fetch`를 교체하지 않고 이 경계를 분리했다.

- 조회: 결제 ID, PortOne 고객사/상점, 채널 key·TEST/LIVE, V2·KG 카드·KRW·주문 금액을 대조한다. PortOne 결제 ID/transactionId와 KG 거래 ID는 별도 필드다. 구매자·카드·영수증·PG 원문은 정규화 결과에 포함하지 않는다.
- 통보: 원문 서명·정수 시간 헤더·알려진 거래 이벤트·상점을 검증한 뒤 **다시 조회해야 한다는 알림**만 반환한다. 이 결과가 결제/환불 원장 확정은 아니다.
- 취소: 취소 직전 잔액을 필수로 전송하고 전액/부분취소 금액을 검증한다. `REQUESTED`를 성공 환불로 바꾸지 않는다. 시간초과, 비정상/알 수 없는 응답, HTTP 실패, 응답 금액 불일치는 결과 불확실로 남기고 자동 재전송하지 않는다.
- 호출 전제: 상위 서비스가 실제 사용자 권한·주문 소유권·조회 결과를 대조하고, 로컬 결제 잠금/멱등 요청 기록을 확보한 뒤 취소 primitive를 호출해야 한다. 이 adapter 자체는 DB·주문·재고·포인트·추첨권을 변경하지 않는다.

감독자가 합성 HTTP 응답과 합성 webhook 서명으로 집중 테스트 **14개 통과, 실패/미실행 0개**를 확인했다. 응답 헤더 후 정지, 완성 JSON을 보낸 후 EOF만 정지하는 경우, 중복/변조 서명, 금액·채널 불일치를 포함한다. 실제 PortOne HTTP·키·채널·결제/환불은 사용하지 않았다. 주문 원장·복구 worker·앱 결제창 연결은 아직 별도 단계이며 `PAYMENT_PROVIDER=UNCONFIGURED`를 유지한다.

## 직접 연동 참고 · INIpay PRO

2026-09-09 사용자가 [INIpay PRO 공식 가이드](https://manual.inicis.com/pay/pro.html)를 지정하고, KG의 결제 허용 승인 후 앱에 적용할 수 있도록 기억해 달라고 요청했다. 해당 페이지의 결제요청·인증·승인·망취소·앱 연동 부분을 확인했다. 실제 구현 시 최신 문서와 승인된 MID의 지원 상품/결제수단을 다시 확인한다. 문서 열람은 계약 완료나 운영 활성화 승인이 아니다.

### 공식 문서에서 확인한 핵심

- PC/모바일 통합 PRO 결제창을 사용한다. 요청 JS는 `https://paypro.inicis.com/std/payment/js/INIPayPro_v2.js`, 요청은 UTF-8 POST다.
- MID와 **모바일 금액위변조 Hash Key**가 필요하다. 기존 조회 adapter의 INIAPI Key와 구분한다. 고유 `P_OID`, 금액, 밀리초 timestamp를 연결한 `P_CHKFAKE`를 요구한다. 정확한 해시/인코딩은 공식 샘플과 대조한다.
- 흐름은 결제요청 → `P_NEXT_URL` 인증결과 → 서버 승인요청 → 최종 승인결과다. `P_AUTH_TID`와 `P_APPL_TID`를 구분한다. 가상계좌는 `P_NOTI_URL` 입금통보도 필요하다.
- 승인 주소는 `https://{P_IDCNAME}paypro.inicis.com/payment/v1/rest/payAppl.ini`, 망취소는 같은 센터의 `payNetCancel.ini`다. 센터 값은 `fc/ks/stg`; 한 운영 호스트로 고정하지 않는다.
- 망취소는 승인 처리 중 예외 복구용이며 일반 환불과 다르다. 문서상 인증 TID 기준 10분/승인 TID 기준 1분 제한이 있으므로 구현 직전 재확인한다.
- Android 외부 결제앱 호출·미설치 처리·패키지 가시성, iOS scheme 등록·앱 복귀를 검증해야 한다. User-Agent 임의 변경은 피한다.
- PRO의 `P_RESERVED`는 JSON으로 설명되지만 앱 참고 부분에는 구버전 INIpayMobile query-string 예시가 섞여 있다. 복귀 옵션은 PRO 샘플/기술지원과 대조한 뒤 확정한다.

### 직접 연동을 선택할 경우의 적용 원칙

다음은 문서 인용이 아니라 DABBOBA의 구현·출시 기준이다.

1. 사업 운영자가 실제 판매 구조에 대한 KG 심사 결과, MID, 이용 가능한 결제수단을 확인한다. 비밀키는 채팅·앱·Git이 아닌 승인된 서버 비밀 설정으로 전달한다.
2. 서버가 주문 금액과 해시를 만들고, 인증/승인 응답의 MID·OID·금액·거래 식별자를 저장된 주문과 대조한다. 앱 복귀나 인증 성공만으로 결제 완료/추첨권 발급을 하지 않는다.
3. 수신 센터 값은 환경별 허용 목록에 매핑한다. 임의 URL을 호출하지 않는다. 중복 callback·승인 시간초과·망취소·조회 대사·일반 취소/환불을 기존 원장과 연결한다.
4. Supabase 중심 실행 방향을 유지하되, 승인 후 실제 서버 통신과 iPhone/Android 결제앱 왕복을 검증한다. 문서의 mixed-content 허용 예시를 그대로 복사하지 않고 HTTPS 및 최소 허용 범위를 사용한다.
5. KG 승인만으로 자동 활성화하지 않는다. 결제창→최종 승인→주문/재고/추첨권→취소·오류 복구 검증과 운영 적용 확인 후 전환한다. 이번 요청에서는 결제 코드·환경값·운영 DB를 변경하지 않았다.

현재 조회 adapter는 PRO 결제창/승인 연동의 대체물이 아니다. 아래 DBB017 검증 수치는 당시 조회 단계 기록이며 최신 전체 출시 상태가 아니다.

## 조회 계약

[KG이니시스 공식 거래조회 매뉴얼](https://manual.inicis.com/pay/etc-inquiry.html)의 INIAPI V1을 사용한다.

- TEST: `https://stginiapi.inicis.com/api/v1/extra`
- LIVE: `https://iniapi.inicis.com/api/v1/extra`
- UTF-8 form-urlencoded POST 한 번으로 조회한다. 승인·취소 API를 호출하거나 요청을 자동 재전송하지 않는다.
- 요청 필드는 `type=Extra`, `paymethod=Inquiry`, KST 시각 `timestamp`, `clientIp`, `mid`, `originalTid`, `hashData`다. SHA-512 대상은 순서대로 `INIAPIKey + type + paymethod + timestamp + clientIp + mid`이며, 문자열을 연결한 뒤 해시하고 전송 값은 form 인코딩한다.
- DB 결제 제공자가 `KG_INICIS`이고 원화·정수 금액·기존 결제 TID가 확인되는 경우만 조회한다. TID가 없으면 UNKNOWN을 유지한다. 주문번호만으로 조회하려면 KG의 별도 계약 조건이 있으므로 임의로 OID 조회로 대체하지 않는다.
- 응답 성공 코드와 TID·금액을 대조한다. 승인/입금완료는 PAID 관측, 입금대기는 PENDING 관측, 취소는 CANCELLED 관측으로 분류하되 **이는 원장 확정이 아니다**. 거래없음이나 알 수 없는 상태는 UNKNOWN이다. 취소 조회만으로 전액 환불 완료를 추정하지 않는다.
- 거래번호·금액 불일치, 응답 오류는 성공으로 인정하지 않는다. 기존 결제 상태와 다른 관측은 MANUAL_REVIEW로 남기고, 오류는 안전한 ERROR 기록 경로로 보낸다. `payments`, `orders`, 재고, 포인트, 추첨권은 조회 결과로 변경하지 않는다.
- URL은 환경별 고정 주소만 사용한다. Redirect는 따르지 않으며 요청과 응답 body에 시간·크기 제한을 둔다. 키·서명·구매자 정보·응답 원문을 로그에 남기지 않는다.

| `PAYMENT_RECONCILIATION_PROVIDER` | 기본 `MANUAL_REVIEW`, 실제 연결 준비 시 `KG_INICIS` |
| `KG_INICIS_ENVIRONMENT` | `TEST` 또는 `LIVE` |
| `KG_INICIS_MID` | 해당 환경에 승인된 KG 상점 ID |
| `KG_INICIS_INIAPI_KEY` | INIAPI 조회용 비밀키. 결제창 SignKey와 혼동하지 않음 |
| `KG_INICIS_CLIENT_IP` | KG 요청에 전달할 서버 IPv4. 실제 배포 경로에서 확인 |

KG를 선택하면 나머지 설정이 모두 필요하다. `MANUAL_REVIEW`인데 KG 설정/키만 남아 있어도 시작을 차단한다. 실제 외부 조회 설정은 명시적인 STAGING+TEST 또는 PRODUCTION+LIVE만 허용한다. LOCAL/TEST에서 실제 KG 설정을 섞거나, 로컬 테스트 명령에 KG 비밀을 상속하지 않는다. 테스트는 합성 값과 응답 대역만 사용한다.

이 설정을 기존 운영 `.env`나 `.env.development.local`, 앱의 public 환경변수에 붙이지 않는다. 비밀 보관·주입 방식은 온라인 실행 환경을 선택한 후 별도로 승인한다. GCP Secret Manager·다른 유료 저장소·스케줄러를 자동 생성하지 않는다.

## 사용자 준비와 후속 순서

1. KG 담당자에게 DABBOBA의 실제 판매 방식과 지원 결제수단·심사 조건을 확인하고, 테스트 MID 및 INIAPI 이용 가능 여부를 준비한다. 비밀키 원문은 채팅에 보내지 않는다.
2. 승인·취소 구현 전에 모바일 결제창 상품과 필요한 별도 키, 결과 수신 주소, 테스트 거래 환경을 확인한다. 카드번호/CVC/비밀번호를 앱이나 DABBOBA DB에 저장하는 방식은 사용하지 않는다.
3. 서버 승인 요청의 중복 방지·불확실 응답 복구·사용자/주문/금액 대조를 연결한다. 기존 generic `x-dabboba-signature` webhook이 KG 원문 callback을 그대로 처리할 수 있다고 가정하지 않는다.
4. 부분/전액 취소·환불 정책과 KG 계약을 확인한 뒤 공급자 요청과 기존 보상 원장을 연결한다. 쿠지 lease 만료, 배송·추첨·포인트 사용 이후의 환불은 자동 성공 처리하지 않는다.
5. 별도 승인된 테스트 환경에서 결제창→승인→조회→취소·환불·중복/타임아웃을 검증한 뒤 출시 판단을 한다. 현재 무료 staging 생성 한도와 온라인 실행 환경 선택은 별도 미완료 항목이다.

## 검증 상태

2026-09-09 구현을 마친 뒤 마지막 검증을 수행했다.

- Worker TypeScript build 성공. Worker 테스트 **77개 통과, 실패·생략 0개**. 별도 로컬 PostgreSQL에서 제한된 worker 역할로 조회 결과의 수동 검토/오류 기록과 결제·주문 상태 보존을 확인했다. KG 응답은 대역이며 실제 KG 서버 호출이 아니다.
- 테스트 환경 사전 차단 검사 3개 통과. 실제 테스트 진입 명령에 합성 KG 비밀값을 주입했을 때 실행이 차단되고 값이 출력되지 않음을 확인했다.
- 웹 build, 모바일 TypeScript, 보호 runtime 검사 28개 통과. 운영·개발 환경 파일, 고정 실행기, 기존 migration 0038/0039, `ops/cloud-run` 파일은 작업 시작 시점과 hash가 일치한다.
- 루트 전체 검사 **528개 중 522개 통과, 6개 실패**. 실패 항목은 이번 수정 범위 밖인 모바일 안내문 스타일 1개(`expo-shell-structure.test.mjs`), 만료 세션 처리 1개(`mobile-customer-auth.test.mjs`), 문의 API·작성·상세 화면 3개(`mobile-inquiry-detail.test.mjs`), 프로필 상품 표시 1개(`mobile-profile-card-visibility.test.mjs`)다. 이 검사들은 소스 코드 형태를 확인하며, 실제 동작 실패인지 검사 기대값 불일치인지는 해당 모바일 변경과 함께 별도 진단해야 한다. 통과를 위해 모바일 코드나 해당 검사를 변경하지 않았다.

이번 결과는 조회 연결 단계의 로컬 검증이다. 실제 테스트 상점 거래, 승인·취소·환불, 운영 원장 변경, 온라인 배포 및 Google Cloud 작업은 수행하지 않았다. 전체 백엔드나 출시 검증 완료로 해석하지 않는다.
